# EventLens 2.8｜上市公司重大事件影响分析 Agent 产品设计文档

**版本**：2.7 Final Delivery  
**目标用户**：买方基金公司专业研究员、研究负责人、基金经理  
**团队假设**：15 位研究员，覆盖消费、医药、科技、新能源等行业；每位研究员同时跟踪约 20–30 只股票。  
**Demo 目标**：至少完整跑通一个“事件输入 → 9 阶段处理 → 结构化报告 → 继续深究 / 新搜索”的场景。

---

## 1. 问题定义

上市公司发布重大事件后，研究团队往往需要在 2–4 小时内回答三个问题：

1. **基本面发生了什么变化？**
2. **相对原有预期和估值，哪些假设需要重算？**
3. **对当前持仓及关联持仓，哪些风险暴露需要复核？**

当前瓶颈并不只是“写报告慢”，而是整个分析链条缺少可复用、可审计的下限：

- 信息分散在公告、交易所、公司 IR、媒体、卖方、行业数据和内部底稿；
- 最危险的错误不仅是“引用错”，还包括“相关公告根本没有看到”；
- 不同研究员对同一事件的分析维度和深度差异很大；
- 财报季存在极端峰值，同一晚可能同时出现大量事件；
- 一次性报告不能形成跟踪闭环；
- 单公司视角无法给 PM 组合级冲击图；
- 过度标准化又可能抹平研究员的 alpha，因此系统需要“标准化下限 + 保留个人判断上限”。

EventLens 的产品定位不是“自动预测涨跌”，而是：

> **把重大事件转化成一份可追溯、可质疑、可继续研究、可被人工覆盖的机构级研判底稿。**

---

## 2. 产品原则

### 2.1 不给简单“利好 / 利空”标签

输出至少覆盖：事件事实、基本面、盈利质量、资产负债表/偿债、预期差、估值、组合影响、反方论证、证据缺口和下一数据点。

### 2.2 事实、推断、假设分层

- **事实**：用户明确提供或有来源支持；
- **推断**：从事实推演出的解释；
- **假设**：估值、情景、概率、目标区间等需要研究员承认的参数；
- **未知**：无法获得或无法合法使用的数据。

### 2.3 召回与完整性是两条独立链

第一轮目标是“找相关资料”；第二轮目标是“主动寻找第一轮漏掉什么”。第二轮应特别覆盖更正、问询、融资、担保、质押、减持、股权激励、监管处罚、并购业绩承诺等可能推翻初判的材料。

### 2.4 报告不是终点

报告下方继续保留研究输入框：

- **继续深究**：基于当前底稿继续拆因果、估值假设和反方；
- **新搜索 · Web**：开启新的公开证据召回；
- **开启新事件**：清空上下文，开始新的事件。

### 2.5 人负责决策，Agent 负责提高下限

系统不自动执行买卖。研究员可以保留自己的模型分支、覆写系统假设，并应留下独立复核痕迹。

## 3. 核心交互：三态工作台

### 状态 A｜确认事件

页面只突出一个主任务：事件描述输入。

可选输入：

- 上市公司与事件描述；
- 组合上下文（真实机构版本应由权限系统读取，而非手填）；
- 事件前内部模型/观点版本。

CTA：**开始研判**。

### 状态 B｜研判运行中

左侧常驻 9 个进程主题，当前任务高亮、已完成任务变为完成态；右侧显示当前步骤正在做什么以及阶段摘要。用户点击开始后界面必须立即进入运行态，不能出现“按钮按了没反应”的空窗。

### 状态 C｜结构化报告 + Research Loop

9/9 完成后，右侧自动切换为研究报告；底部继续保留研究输入和两种模式：继续深究 / 新搜索。

## 4. 9 阶段 Agent 架构

```text
用户事件
  ↓
01 确认事件与主体
  ↓
02 重要性分诊
  ↓
03 多源证据召回 ─────────────┐
  ↓                           │
04 完整性与口径对账（独立链） │
  ↓                           │
05 基本面与财务传导           │
  ↓                           │
06 预期差与估值重估           │
  ↓                           │
07 组合影响映射               │
  ↓                           │
08 Challenger + Verifier ─────┘
  ↓
09 综合研判报告
  ↓
继续深究 / 新搜索 / 新事件
```

### 01 确认事件与主体

目标：只提取用户明确写出的主体、市场、时间、事件类型和事实，不使用常识补齐未提供数字。

A/H/ADR 等场景要区分 `issuer` 与 `security`，不能把证券代码当作唯一公司身份。

### 02 重要性分诊

建议等级：

- **P0**：潜在违约、重大监管、控制权、重大造假/流动性等需即时升级；
- **P1**：可能改变盈利预测、估值或持仓逻辑；
- **P2**：需要记录但不需要完整深度研判；
- **NULL**：正确答案就是“无重大变化，归档”；
- **HOLD**：信息不足但可能重大，不能假装 NULL。

NULL 事件应输出短卡并静默归档，避免 alert fatigue。

### 03 多源证据召回

生产版召回来源应包括：

- 交易所 / 巨潮 / 港交所等官方披露；
- 公司官网、IR、业绩说明会；
- 许可范围内的 Wind / Bloomberg / 卖方等机构数据；
- 可靠媒体与行业数据；
- 权限允许的内部模型、纪要和研究底稿。

当前 Demo：真实 LLM 模式使用 OpenAI Responses API 的 `web_search` 作为公开网络检索入口；离线 / Mock 模式使用合成数据。

### 04 完整性与口径对账

这不是“再搜一遍相同关键词”，而是独立漏检检测：

- 更正 / 补充公告；
- 交易所问询与回复；
- 债务融资 / 契约；
- 担保、质押、大股东资金占用；
- 并购对价、PPA、商誉、业绩承诺；
- 旧简称、借壳前主体、A/H 多证券身份；
- 报告与后续更正的时点链。

完整性状态不能只有“成功/失败”，至少应有：`complete / partial / unknown / source_unavailable`。

### 05 基本面与财务传导

分析覆盖范围：

- 收入：量、价、结构、分部；
- 利润：毛利、费用、税、少数股东损益、一次性项目；
- 现金：CFO、应收、存货、资本开支；
- 资产负债表：净债务、受限现金、到期缺口、契约；
- 融资：增发、可转债摊薄、再融资；
- 并购：对价、PPA、商誉、业绩承诺；
- 外汇：交易损益与 OCI/折算分开；
- 治理红旗：关联交易、客户集中、货币资金/理财、大股东资金往来等。

如果分部披露充分，可以进入 SOTP；如果分部边界或利润口径不足，应明确拒绝伪精确估值。

### 06 预期差与估值重估

核心不是“新闻好不好”，而是：

> **相对于事件发生前，市场/内部模型已经预期了多少？现在需要改哪些假设？**

可用输入：

- 冻结时点的内部模型；
- 一致预期与卖方调整轨迹；
- 北向、融券、成交拥挤度等辅助 price-in 线索；
- 历史同类事件。

这些数据不存在时必须显示不可判断，不构造“市场已经 price in 70%”之类伪精度结论。

### 07 组合影响映射

单公司不是终点。生产版需把同一事件映射到：

- 事件主体；
- 上下游；
- 同业竞争者；
- 受益端与受损端；
- 未知暴露；
- 不同基金/策略/权限域。

组合层应同时显示净贡献和绝对贡献，避免净额掩盖多空两边都很大的风险。

### 08 Challenger + Verifier

Challenger 的任务是“击倒当前论点”，Verifier 的任务是“逐条核验”。

运行时控制建议：

- 引用必须能回到真实来源；
- 数值、币种、期间、合并口径单独检查；
- 来源不支持的结论降级；
- 相互冲突的来源进入 HOLD / 人工复核；
- 模型升级必须经过回归集 / canary，避免静默改变输出。

当前 Demo 在真实模式下会在 Challenger 阶段再次执行公开 Web Search，并返回 URL citation；自由语义完整蕴含验证仍属于生产能力，不在 Demo 中冒充已经解决。

### 09 综合研判报告

最低结构：

1. 结论先行；
2. 事件解构；
3. 基本面与财务；
4. 预期差与估值；
5. 组合影响；
6. 反方与失效条件；
7. 证据缺口；
8. 下一步验证。

## 5. Research Loop：把一次性报告变成持续研究

报告生成后，研究员可以继续：

### 继续深究

后端携带当前报告和最近追问历史，回答新的因果、估值、风险问题，但不重新生成整份报告。

### 新搜索 · Web

开启新的公开搜索链，新增证据追加到当前研究线程，不覆盖原始报告。典型问题：

- 是否有新的更正公告？
- 有没有交易所问询？
- 债务、担保、质押是否改变当前判断？
- 有没有公开信息能推翻当前海外增长论点？

### 生产版进一步闭环

```text
事件 → 论点 → 跟踪项 → 到期数据 → 自动比对 → 重开论点 → 复议
```

当前可交付 Demo 已实现“报告后继续研究”的交互与 API；自动定时监控、通知队列和持久化复议工作流属于生产化下一层。

## 6. 财报季峰值、成本与容量设计

15 人团队在 4 月、8 月等峰值期必须处理“同时到达”而不是平均吞吐。

生产容量模型需要显式参数：

- 每事件预计 token / 工具调用预算；
- RPM / TPM / 并发槽；
- P0 预留容量；
- 研究员每人最大在途数；
- 经理复核队列；
- 缓存与去重命中率；
- 降级顺序。

推荐降级顺序：

1. 保留 P0 / P1 主体事实与风险筛查；
2. 降低历史对标深度；
3. 延后低相关二阶组合扩散；
4. P2 只生成短卡；
5. NULL 静默归档并抽检。

商业论证不能只写“节省时间”。试点应测：净节省工时、人工复核率、重大缺陷率、漏检率、重开论点率、许可证/模型/平台成本和有效产能兑现率。

## 7. 合规与数据治理

生产版必须额外实现：

- 研究 / 投资、公募 / 专户等信息墙；
- MNPI / 非公开专家纪要的入口拦截；
- 付费数据 read/store/index/embed/external inference 的逐动作许可；
- 服务端身份与最小权限；
- 不可篡改审计日志、签名、WORM、保留周期；
- 数据导出与研究记录要求的法务确认。

**当前 Demo 的浏览器 JSON、Mock 数据和本地日志不应被称为合规留档。**

---

## 8. A 股 / 港股本土事件语法

事件分类器需要识别本土披露阶段和语义：

- 业绩预告 → 业绩快报 → 正式年报/中报 → 更正；
- 问询函及回复；
- 停复牌；
- 减持规则与回购；
- 股权激励费用；
- 政府补助；
- 商誉 / 对赌 / 业绩承诺；
- VIE；
- 中报未审计状态；
- A/H 同发行人多证券；
- 再融资、可转债、担保、质押。

时点分析必须保存当时可获得的版本，后发更正不能倒灌旧快照。

---

## 9. 人机协作与 alpha 保护

标准框架只保证“分析下限”，不能把所有研究员训练成同一种观点。

建议机制：

- 研究员先记录独立初判，再解锁 AI 底稿；
- 记录是否检查原文、是否复算关键数值、是否改变假设；
- 团队历史底稿按权限、事件类型和冻结时点做 few-shot；
- 研究员保留个人模型分支；
- 复盘“AI错在哪里 / 人错在哪里 / 哪个假设导致偏差”；
- 反馈进入具体责任模块的回归集，而不是只存一条备注。

## 10. Demo 技术架构

### 10.1 离线模式

```text
打开Demo.html
  ↓
浏览器本地状态机
  ↓
9 阶段固定流程 + 合成场景
  ↓
报告 + 继续深究 / 模拟新搜索
```

无需 Node、API Key 或网络，适合产品演示。

### 10.2 Mock 后端模式

```text
浏览器 → Node server.js → data/mock_stage_outputs.json
```

用于验证真实请求/流式状态机，不产生 API 费用。

### 10.3 真实 LLM 模式

```text
浏览器
  ↓ /api/analyze (NDJSON)
Node.js Orchestrator
  ↓
OpenAI Responses API
  ├─ GPT-5.6 Sol：财务、估值、报告等复杂阶段
  ├─ GPT-5.6 Luna：轻量阶段
  └─ web_search：召回、完整性、Challenger、新搜索
  ↓
结构化报告 + URL sources
```

API Key 只放在后端 `.env`，不进入 HTML。

当前 OpenAI API 文档中，GPT-5.6 Sol / Luna 支持 Responses API 和 Web Search；新集成使用 `web_search`，而不是旧的 `web_search_preview`。

## 12. 上生产环境：AI Agent 实践需要考虑的关键问题

本节直接回答：**基于“上市公司重大事件影响分析”这一场景，如果 EventLens 从 Demo 进入基金公司的生产环境，在 AI Agent 实践方面需要重点考虑什么。**

Demo 能证明“输入 → Agent 处理 → 结构化输出”的产品链路可行，但生产环境的难点不是把 Prompt 写得更长，而是把 **数据、Agent 编排、模型可靠性、权限合规、容量成本、人工复核和持续运营** 做成可测、可降级、可追责的系统。

### 12.1 数据接入：先解决“看全”，再解决“看懂”

**场景风险**：研究员最怕的不只是引用错，而是漏掉一份足以推翻结论的更正公告、问询回复、债务说明或监管文件。

**生产要求**：

- 建立交易所/巨潮/港交所、公司 IR、许可范围内金融数据、可靠媒体和内部研究库的多源连接器；
- 对 PDF、HTML、XBRL、扫描件、表格与附注建立统一解析层；
- 建立 issuer/security/entity 主数据，解决简称变更、借壳、A/H/ADR 多证券身份；
- 将“第一轮召回”和“第二轮完整性对账”拆成独立链路，不能用同一组关键词自证完整；
- 对目录、水位、游标和 source health 做监控，来源不可用时输出 `unknown/source_unavailable`，而不是假装“没有相关公告”。

**验收**：用冻结时点历史事件构建“应召回文档金标准”，分别测 Recall、关键文档漏检率、重复率和来源不可用时的降级行为。

### 12.2 Agent 编排：每个 Agent 要有职责、输入、输出和停止条件

**场景风险**：如果所有任务都交给一个大 Prompt，事实、推断、估值和组合建议容易互相污染，也很难定位错误发生在哪一层。

**生产要求**：

- Orchestrator 只负责任务分解、路由、状态和预算，不替分析节点偷偷补结论；
- 召回、完整性、财务、估值、组合、Challenger、Verifier 分工明确；
- 每个节点定义结构化输入/输出 schema、超时、重试次数和失败状态；
- 只将经过校验的事实表传给下游，避免多个 Agent 各自“记住”不同版本数字；
- 工具调用和模型调用设置 token、时间、费用预算，到阈值时可返回 partial，而不是无限搜索。

**验收**：做节点级单测、端到端状态机测试、故障注入和依赖链追踪，能够回答“哪一步、基于什么证据、改变了哪一个结论”。

### 12.3 LLM 可靠性：不能把“写得像研究报告”当作正确

**场景风险**：金融报告语言天然具有说服力，引用幻觉、数字口径错误和未经支持的因果判断会被漂亮文本掩盖。

**生产要求**：

- 每条关键事实绑定来源定位，不只保存 URL；
- 数值、单位、币种、期间、合并范围、同比/环比口径由确定性代码再次校验；
- 财务公式和估值计算尽量由代码执行，LLM 负责解释和提出假设；
- unsupported claim 必须降级为“推断/待验证”，不能进入高置信结论；
- 冲突来源进入 HOLD 或人工复核；
- Challenger 与主分析链尽量保持独立，主动寻找能够推翻当前论点的证据。

**验收**：逐条 claim-level citation correctness、numeric accuracy、unsupported-claim rate、冲突处理率和专家盲评。

### 12.4 模型非确定性与版本升级：同一事件不能悄悄变结论

**场景风险**：同一输入重复运行可能出现不同叙事；模型供应商升级后，输出风格甚至核心判断可能静默改变。

**生产要求**：

- 固定模型版本、系统提示、工具配置、证据快照和分析时点；
- 保存运行版本、Prompt/Policy 版本、输入证据哈希和输出摘要；
- 模型升级前跑冻结回归集和 canary；
- 对关键结论差异设置自动 diff 和人工放行门槛；
- 高风险事件可采用双模型/双路径复核，但不能把“多数投票”误当作事实验证。

**验收**：冻结输入重复运行的关键字段稳定率、版本升级回归失败率、canary 差异率和回滚演练。

### 12.5 重要性分诊：先判断“值不值得分析”，避免狼来了

**场景风险**：财报季大量低价值公告如果全部生成长报告，会制造 alert fatigue，反而淹没真正的 P0/P1 风险。

**生产要求**：

- 建立 P0/P1/P2/NULL/HOLD 分诊；
- NULL 事件只生成短卡并静默归档，同时保留抽检；
- 信息不足但潜在重大的事件必须是 HOLD，而不能被归为 NULL；
- 重大流动性、控制权、监管、违约等硬风险可以覆盖普通优先级规则直接升级。

**验收**：除了重大事件 precision/recall，还必须做 NULL test，测无重大变化事件的正确静默率和漏掉重大事件的 false negative。

### 12.6 财报季峰值、成本与降级：设计 burst，不设计平均值

**场景风险**：15 名研究员覆盖约 300–450 个公司关系，在 4 月和 8 月可能同一晚同时收到大量公告，2–4 小时窗口会被并发挤爆。

**生产要求**：

- 建立每事件 token / tool-call / 搜索预算和预计成本；
- 同时管理 RPM、TPM、模型并发槽、搜索并发、解析队列和人工复核队列；
- 给 P0/P1 预留容量；
- 缓存相同公告解析结果，对多研究员共同覆盖的事件去重；
- 明确过载降级：保留主体事实和硬风险 → 降低历史对标 → 延后二阶扩散 → P2短卡 → NULL静默；
- 不只测机器 SLA，还要测“机器完成后人是否有能力在窗口内复核”。

**验收**：用财报季 burst 回放做压力测试，报告 P50/P95 延迟、排队长度、超时率、每事件成本和人工 backlog。

### 12.7 Human-in-the-loop：防自动化偏见，同时保护 alpha

**场景风险**：带引用、结构漂亮的 AI 初稿可能降低研究员质疑意愿；另一方面，过度标准化会把真正有价值的研究员差异磨平。

**生产要求**：

- 对关键事件要求研究员先记录独立初判，再查看 AI 底稿；
- 记录是否打开原文、是否复算关键数字、是否修改假设，而不是只记录“点击批准”；
- 系统标准化分析维度，但允许研究员保存个人模型分支和不同估值框架；
- 将“AI错、人错、数据错、假设错”的原因分类进入评测和回归集；
- 历史 few-shot 只能在权限和时间点允许的情况下调用，避免后视偏差和跨团队污染。

**验收**：研究员独立初判覆盖率、关键数字复算率、AI覆写率、覆写原因、重大缺陷发现率，以及不同研究员分支是否被保留。

### 12.8 权限、MNPI 与付费数据许可：金融 Agent 不能只做“最小权限”四个字

**场景风险**：Agent 可能接触专户持仓、内部调研、专家访谈、潜在 MNPI 或受再分发限制的 Wind/Bloomberg 数据。即使模型分析正确，也可能因为数据使用方式不合法而不能上线。

**生产要求**：

- 研究/投资、公募/专户、不同策略之间建立服务端信息墙；
- 每个证据对象携带权限域、来源许可、可执行动作（read/store/index/embed/external inference/export）；
- 对疑似 MNPI、泄露文件、未经批准专家纪要进行入口拦截和人工升级；
- API Key、持仓和内部文档不进入前端；
- 审计记录使用签名、不可篡改存储/WORM和明确留存周期；
- 具体是否满足基金业协会/证监会及数据供应商合同要求，需要法务与合规在机构环境内确认，Demo 不能代替该结论。

**验收**：越权测试、跨域污染测试、MNPI 流程演练、供应商许可矩阵检查和审计记录完整性验证。

### 12.9 持续研究闭环：Agent 的价值不应在“生成报告”时结束

**场景风险**：一次研判通常建立在几个待验证假设上；如果下一数据点出来后系统没有自动回看，报告很快成为一次性消耗品。

**生产要求**：

- 将报告中的关键假设转成结构化 tracking item：指标、期间、单位、阈值、来源、负责人、论点版本；
- 新数据到达后自动比对实际值和原假设；
- 触发条件满足时只重跑受影响节点，并“重开论点”；
- 重复数据幂等处理，更正数据保留历史；
- 复议后的新判断形成新版本，不能悄悄覆盖旧版本。

**验收**：触发准确率、重复通知率、更正处理、thesis reopen 成功率、从数据到达至复议的时延。

### 12.10 生产监控与 Eval：把错误变成可运营指标

**场景风险**：Agent 不是一次上线后长期不变的软件模块；数据源、模型、Prompt、工具和团队行为都会变化。

**生产要求**：

- 在线监控数据源健康、解析失败、搜索失败、模型 429/5xx、token/成本、延迟、阶段失败和人工队列；
- 离线维护按行业/事件类型分层的金标准评测集；
- 将研究员覆写、结论被推翻原因和跟踪结果反馈给具体责任模块；
- 评测不仅看“报告是否好看”，还看召回、事实、计算、预期差、组合映射、NULL、人工复核和稳定性；
- 任何生产指标退化超过门槛时支持降级到规则/人工流程，而不是强制继续使用 Agent。

**验收**：建立上线门槛和持续 SLO，包括关键召回率、claim 支持率、数字正确率、P95时延、每事件成本、人工重大缺陷率、NULL误报/漏报、模型版本回归结果。

### 12.11 从 Demo 到生产的放行逻辑

EventLens 不应以“Demo 可以调用大模型并生成完整报告”作为上线标准。生产放行至少需要同时满足四类门槛：

| 门槛 | 需要证明的事情 |
|---|---|
| **研究正确性** | 关键证据召回、事实/数字/口径、反证与估值输入达到专家认可的质量线 |
| **系统可靠性** | 峰值并发、超时、失败恢复、幂等、版本管理与降级能够在真实 SLA 下工作 |
| **合规安全性** | 权限域、MNPI、付费数据许可、审计与留存经过机构合规/法务确认 |
| **人机有效性** | 在不显著增加重大缺陷或自动化偏见的前提下，真实释放研究时间并改善团队响应一致性 |

最终生产试点应采用**冻结时点历史回放 + 小规模真实 shadow mode + 人工并行**。先证明“不漏重大事项、不制造虚假确定性、失败时能安全降级”，再逐步扩大覆盖，而不是直接将 Agent 输出视为投资决策。

## 双语交互层（v3.0）

同一套 EventLens Agent 支持中文与 English。用户可在顶部语言切换器中选择语言；选择结果同时控制界面、9 个 Agent 阶段名称、真实 LLM System Prompt/阶段 Prompt、最终报告与 Research Loop 后续追问。切换语言时，未修改的内置示例会自动切换为对应语言版本；用户自行输入的事件与组合上下文会保留原文，避免静默改写研究输入。

离线 Demo 为每种语言提供对应的合成案例输出；真实 LLM 模式则在请求体中传递 `language=zh|en`，后端据此选择语言专属 Prompt。语言切换不改变事实、证据、计算规则与风险控制，只改变呈现与生成语言。
